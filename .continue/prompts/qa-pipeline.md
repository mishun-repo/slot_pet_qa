Выполни полный Enterprise QA-пайплайн для тикета: {{{ input }}}

Работай строго по этапам. Не пропускай шаги и не скрывай ошибки.

### Этап 1. Разведка тикета и кодовой базы
1. Извлеки ключ тикета из URL и через MCP `jira` получи: Summary, Description, Acceptance Criteria, комментарии и связанные тикеты.
2. Проанализируй изменения или релевантные файлы в `../slot_pet_project` (UI-компоненты, API-роуты, бизнес-логику слота).
3. Если приложение ещё не запущено локально, проверь доступность и при необходимости подскажи/запусти dev-сервер или Docker Compose.

### Этап 2. Тест-дизайн и запись в Google Sheets
1. Спроектируй тест-кейсы (Positive, Negative, BVA, Edge Cases, Domain Invariants).
2. Через MCP `google-sheets` прочитай текущий лист `TestCases` (чтобы определить следующий свободный `TC_ID`, например `TC-045`) и запиши новые кейсы в таблицу `Slot Project - Test Management` (лист `TestCases`).
3. Выстави `Automation_Status = In Progress`.

### Этап 3. Генерация автотестов
1. Создай новую git-ветку в `slot-pet-qa`: `qa/<JIRA_KEY>-auto`.
2. Если нужно, используй MCP `playwright` для открытия запущенного приложения и снятия точных селекторов/структуры API-ответов.
3. Напиши автотесты в `tests/e2e/` (и/или `tests/api/`) с использованием Page Objects и фикстур. Поставь в коде ссылки на `TC_ID` и `JIRA_KEY`.

### Этап 4. Автономный запуск и Triage
1. Запусти только что написанные тесты через терминал (с генерацией JSON/HTML-отчёта и trace при падении).
2. Если тест упал:
   - Проведи triage: это ошибка теста/локатора или реальный баг в `slot_pet_project`?
   - Если ошибка теста — исправь и перезапусти (до 2 попыток).
   - Если это **реальный баг продукта** — переходи к Этапу 5.

### Этап 5. Документирование багов и Bug-to-Regression Loop
Для каждого найденного бага:
1. Собери доказательства: точные шаги воспроизведения, ожидаемый и фактический результат, выдержку из консольных/сетевых логов, путь к скриншоту/трейсу.
2. Через MCP `jira` создай тикет с типом `Bug` в том же проекте, привяжи его к исходному тикету (`relates to` / `blocks`).
3. Через MCP `google-sheets` добавь запись на лист `BugLog` и обнови статус связанного `TC_ID` на листе `TestCases` (`Last_Run_Status = Failed`, укажи `Bug_Link`).
4. **Автоматизация регресса**: создай отдельный сценарий в `tests/regression/bug-<BUG_KEY>.spec.ts` (или `.py`), пометь его тегами `@regression @bug-<BUG_KEY>` и `test.fail()` / `pytest.mark.xfail(reason="JIRA-<BUG_KEY>")` (чтобы CI не блокировался до фикса, но факт регресса отслеживался).

### Этап 6. Финализация в Google Sheets и Merge в GitHub
1. Обнови `Automation_Status = Automated` для всех реализованных `TC_ID` в Google Sheets.
2. Прогони линтер и весь набор стабильных тестов.
3. Сделай commit и push ветки `qa/<JIRA_KEY>-auto`.
4. Через MCP `github` создай Pull Request в `main` с подробным описанием:
   - Ссылка на Jira-тикет и Google Sheet
   - Список добавленных тестов и покрытие AC
   - Список заведённых багов (если есть) и созданных regression-сценариев
5. Дождись запуска GitHub Actions CI. Если все проверки зелёные — включи auto-merge (или выполни merge, если политика репозитория позволяет) и верни мне итоговый отчёт со всеми ссылками.
